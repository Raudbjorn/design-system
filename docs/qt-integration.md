# Qt 6 integration guide

How `@svnbjrn/design` styles a Qt 6 Widgets application — PySide6 desktop
apps, kiosks, and tooling UIs.

None of the 28 Svelte components are involved. The Qt adapter is a token
projection: a generated Qt Style Sheet, a generated QPalette role map, and a
thin Python runtime helper, all derived from the same DTCG sources that
produce the web CSS, the ExtJS sheets and the TUI palette.

## What ships

| Artifact | Contents |
| --- | --- |
| `@svnbjrn/design/qss/dark.qss` (and `light`, `amber`) | Full Qt Style Sheet: status helpers, widget rules, font stack |
| `@svnbjrn/design/qt/dark.palette.json` (and `light`, `amber`) | QPalette role map: `active`/`inactive`/`disabled` groups (14 roles each) plus the status foreground/background pairs |
| `@svnbjrn/design/qt` | `emitQtPalette`, `QT_ROLES`, `QtPaletteInput` — the pure emitter behind the committed JSON |
| `bin/sv_design_qt.py` | Runtime helper: closed-schema validator, `apply()`, `set_variant()`, `watch_color_scheme()`, `load_fonts()` |
| `bin/qt-theme-install.sh` | Copy-only vendoring installer for Python projects |
| Fonts (opt-in) | The bundled WOFF2 files, copied into `<dest>/sv-fonts/` |

All palette documents and sheets are generated by `pnpm run tokens` and
committed. Never hand-edit them: change the DTCG source, regenerate, commit
the outputs. A drift-guard test (`scripts/generated.test.mjs`) fails the
build otherwise.

## Vendoring into a Python project

The installer copies the helper, one theme's QSS, and its palette JSON flat
into an **existing** destination directory — typically an importable Python
package inside your project. It is copy-only: preflight completes before any
write, repeated installation is idempotent, and nothing is deleted.

```bash
# from a checkout, or node_modules/@svnbjrn/design after `pnpm run build`
bash bin/qt-theme-install.sh --theme amber --dest your_package/theme --from . --fonts
```

- `--theme dark|light|amber` selects the artifacts; stems have no `theme-`
  prefix (`amber.qss`, `amber.palette.json`, `sv_design_qt.py`).
- `--from` defaults to the package root beside `bin/`. The installer resolves
  one complete artifact root in order: `<root>/dist`, then `<root>/src/lib`,
  then `<root>` itself. A layout is complete only when it carries both
  `qss/<theme>.qss` and `qt/<theme>.palette.json` — candidates are never mixed.
- `--fonts` copies every WOFF2 into `<dest>/sv-fonts/`; without it no font
  destination is created or inspected.
- Exit codes: `0` installed, `2` argument error (bad/duplicate flags, unsafe
  theme name), `1` preflight/filesystem error (missing destination, incomplete
  layout, missing helper) — preflight failures create and copy nothing.

## Application setup

Load the helper the documented way (importlib from a path), then apply a
theme. `apply()` reads both artifacts and validates the palette before mutating
the application, then calls Fusion → palette → QSS exactly once each:

```python
import importlib.util
from pathlib import Path

from PySide6.QtWidgets import QApplication

theme_dir = Path("your_package/theme")
spec = importlib.util.spec_from_file_location("sv_design_qt", theme_dir / "sv_design_qt.py")
sv = importlib.util.module_from_spec(spec)
assert spec.loader is not None
spec.loader.exec_module(sv)

app = QApplication([])
sv.load_fonts(theme_dir / "sv-fonts")                                    # best-effort
sv.apply(app, theme_dir / "amber.qss", theme_dir / "amber.palette.json")
```

The order matters:

1. **Fusion style first.** Qt's default styles are platform styles; Fusion is
   the deterministic, stylesheet-friendly base every generated value assumes.
2. **Palette underlay.** The generated QPalette colors every role Qt paints
   itself, so Qt-owned widgets with no explicit QSS rule still read the theme
   instead of the platform defaults.
3. **QSS last.** Where the sheet defines a widget it wins over the palette —
   that precedence is deliberate: QSS is the authoritative surface, the
   palette is the fallback beneath it.

A corrupt or hand-edited palette document raises `ValueError` from the
closed-schema validator before any app mutation — an invalid document never
becomes a partially themed application.

## Variant widgets

Dynamic properties do not restyle on their own in Qt. The committed QSS
carries `QLabel[class="…"]` status rules; flip the property and re-polish
through the helper instead of duplicating the four calls everywhere:

```python
sv.set_variant(label, "info")   # setProperty → unpolish → polish → update
```

The palette JSON also carries `success-bg`, `error-bg`, `warning-bg`, and
`info-bg` for consumers that render filled status surfaces. The bundled helper
and QSS currently use the status foreground colors only.

## Following the OS color scheme

`watch_color_scheme()` connects your callback to
`QStyleHints.colorSchemeChanged` when the installed Qt exposes it, and returns
`True`; on older bindings it returns `False` without raising. The callback
owns artifact selection — pick dark or light and re-run `apply()` from the
committed artifacts rather than reading the live palette back:

```python
from PySide6.QtCore import Qt

def on_scheme_change(scheme) -> None:
    name = "light" if scheme == Qt.ColorScheme.Light else "dark"
    sv.apply(app, theme_dir / f"{name}.qss", theme_dir / f"{name}.palette.json")

if sv.watch_color_scheme(app, on_scheme_change):
    ...  # wired
```

`amber` is never auto-selected — like `data-theme="amber"` on the web, it is
an explicit user choice. In Qt terms: point `apply()` at the amber artifacts
only when the user picks that theme, never from the OS scheme callback.

## Fonts

`load_fonts()` scans one directory level for `.ttf`/`.otf`/`.woff2` in sorted
order, registers what Qt accepts, skips the `-1` ids Qt rejects, and returns
the registered family names. It is deliberately best-effort: Qt only
guarantees TrueType/OpenType, and WOFF2 registers where the platform font
engine decodes it (FreeType with brotli — standard on Linux). Elsewhere the
rejected files are skipped and an empty list is normal — the QSS font stack
falls back to the system fonts and theme application continues either way.
The same applies when `sv-fonts/` was never vendored (`--fonts` omitted):
`load_fonts()` returns `[]` without raising.

## Pure emitter

The committed JSON is produced by a public, pure emitter — use it directly to
generate custom palettes:
```js
import { emitQtPalette, QT_ROLES } from '@svnbjrn/design/qt';
import { dark } from '@svnbjrn/design';

const json = emitQtPalette({
  name: 'dark',        // ^[a-z][a-z0-9-]{0,63}$ — doubles as the filename stem
  palette: dark        // Record<TokenName, '#rrggbb'> — any prepared 23-key palette
});
```

It is deterministic (same input, same bytes), validates the theme name before
reading colors, and throws on a missing or non-hex token rather than emitting
a document with holes. There is intentionally no `design-generate --qt`: the
emitter is the prepared extension point.

## QPalette JSON vs `tokens/resolved/*.tokens.json`

Both are committed flat JSON, but they are different projections:

- `qt/<name>.palette.json` is Qt-specific — QPalette role groups plus the
  status pairs, validated by `bin/sv_design_qt.py`'s closed schema.
- `tokens/resolved/<name>.tokens.json` is the broader cross-platform map:
  every token's `css`/`qt` values plus derived hover/pressed states. Use it
  for scale-driven or derived-token work the palette document does not carry.

## The palette is a best-effort underlay

Qt's own documentation cautions that `QApplication.setPalette()` and style
sheets are not fully compatible together, and that native platform styles may
ignore palette roles entirely (see
[`QApplication::setPalette`](https://doc.qt.io/qt-6/qapplication.html#setPalette)
and [`QPalette`](https://doc.qt.io/qt-6/qpalette.html)). The implementation
accepts that trade on purpose: the palette underlay covers Qt-owned widgets
the generated QSS does not reach, while the QSS remains the authoritative
surface — it already styles `QMenu`, menus included. Native dialogs
(file pickers, message boxes) are painted by the platform and are not themed
by either mechanism. Do not build expectations on native-dialog appearance.

## Regeneration and drift

```bash
pnpm run tokens        # regenerates every committed output, including the Qt JSON
pnpm test              # scripts/generated.test.mjs byte-compares them to the emitters
```

The palette documents, QSS sheets, and the `AMBER`/`DARK`/`LIGHT` TUI
constants are all drift-guarded the same way; a hand-edited output fails the
build.

## Not covered

QML/QtQuick (the QSS format does not apply there), QProxyStyle custom
painting, icon recoloring, and per-campaign generated Qt themes (world
packages still extend only dark or light). The `@svnbjrn/design/qt` emitter
API is the extension point for those directions.
