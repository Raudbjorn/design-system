# ExtJS / Proxmox integration guide

How `@svnbjrn/design` styles an ExtJS 7 classic-toolkit UI — Proxmox VE,
Backup Server and Mail Gateway, or your own app built on
proxmox-widget-toolkit.

None of the 28 Svelte components are involved. The adapter is a token
projection: a generated CSS override sheet that restyles ExtJS's own widgets
(`.x-btn`, `.x-grid`, `.x-window`, …) from the same DTCG sources that produce
the web CSS, the Qt style sheets and the TUI palette. Components that have no
ExtJS counterpart simply do not appear.

## What ships

| Artifact | Contents |
| --- | --- |
| `@svnbjrn/design/extjs/theme-sv-dark.css` | Self-contained sheet: `@font-face` block, `:root` variables, `.x-*` rules |
| `@svnbjrn/design/extjs/theme-sv-light.css` | Same, light theme |
| `@svnbjrn/design/extjs` | `emitExtJsCss`, `extJsInputsFromWorldTheme`, `checkProxmoxThemeName` — for generated world themes |
| `bin/proxmox-theme-install.sh` | Installer for a Proxmox node |

Both sheets are generated by `pnpm run tokens` and committed. Never hand-edit
them: change the DTCG source, regenerate, commit the outputs. A drift-guard
test fails the build otherwise.

## Proxmox VE / PBS / PMG

A Proxmox theme is a plain CSS file in the widget toolkit's themes directory,
loaded *after* `theme-crisp-all.css`, and selected by a per-product cookie.
There is no supported extension hook, so the installer does the copying and
(optionally) the one patch needed to make the theme appear in the picker.

```bash
# from a checkout, or node_modules/@svnbjrn/design after `pnpm run build`
scp dist/extjs/theme-sv-dark.css dist/fonts/*.woff2 bin/proxmox-theme-install.sh root@node:/tmp/
ssh root@node
/tmp/proxmox-theme-install.sh install /tmp/theme-sv-dark.css --fonts /tmp --register --apt-hook
```

- `--fonts <dir>` copies the four woff2 files into `themes/sv-fonts/`, where
  the sheet's `@font-face` rules expect them. Omit it and the theme falls back
  to the system font stack — everything else still applies.
- `--register` adds one entry to `Proxmox.Utils.theme_map` in `proxmoxlib.js`
  so the theme shows up in the UI's theme picker. Without it the theme still
  works; you just have to set the cookie yourself:

  ```js
  document.cookie = 'PVEThemeCookie=sv-dark; path=/; max-age=31536000'
  ```

  The cookie is `PVEThemeCookie` on VE, `PBSThemeCookie` on Backup Server,
  `PMGThemeCookie` on Mail Gateway.
- `--apt-hook` installs `/etc/apt/apt.conf.d/99-svnbjrn-design-theme`, which
  re-applies the registration after a `proxmox-widget-toolkit` upgrade
  overwrites `proxmoxlib.js`. APT has no per-package post-invoke, so the hook
  runs after *every* `dpkg` invocation — it is a no-op when the registration is
  already present. It calls the `register` verb, which re-registers every
  installed sheet and touches nothing else; its output goes to the journal
  (`journalctl -t svnbjrn-design`) rather than `/dev/null`, so a failure there
  leaves a trail.

The installer only ever writes or deletes files carrying its own header
marker. Names like `crisp` and `proxmox-dark` satisfy Proxmox's rule too, so
installing under one of those would otherwise silently replace a file the
distribution owns and dpkg would restore on the next upgrade; that is refused
instead.

`proxmox-theme-install.sh status` reports what is installed, whether it is
registered, and whether the file is actually reachable over HTTPS.
`proxmox-theme-install.sh uninstall sv-dark [--purge-fonts]` reverses
everything; every patch is preceded by a timestamped backup, and a patch that
does not verify is rolled back rather than left half-applied.

One sheet covers all three products — they share the widget toolkit and its
themes directory. Only the cookie name and the URL prefix (`/pwt/themes/` vs
`/widgettoolkit/themes/`) differ. Proxmox Datacenter Manager is *not* covered:
it is a Yew application, not ExtJS.

`index.html.tpl` is never touched. That is what older community themes patch,
and it is the part that breaks loudly on upgrade.

## Your own ExtJS app

Load the sheet after ExtJS's own CSS:

```html
<link rel="stylesheet" href="ext-all.css">
<link rel="stylesheet" href="theme-crisp-all.css">
<link rel="stylesheet" href="theme-sv-dark.css">
```

Keep the `sv-fonts/` directory beside the sheet, or drop the `@font-face`
block and serve the fonts however you already do.

Nothing is wrapped in a cascade layer. Layered rules lose to unlayered ones,
and ExtJS's stylesheets are unlayered — a layer here would make the whole
theme inert.

## World themes

The seed generator emits sheets directly:

```bash
pnpm exec design-generate --seeds "#8a4b2f,#2f6f8a" --name mistwood \
  --hints grimdark --extjs theme-sv-mistwood.css
```

stdout still carries exactly one JSON document; the CSS goes to the named
file, diagnostics to stderr. The generated package only carries colors (and
sometimes radii), so the emitter folds it over the resolved tokens of the
theme it extends — everything the world leaves alone comes from `dark` or
`light`, and hover/pressed states are recomputed from the *overridden* colors.

**Names are constrained.** VE and PMG validate the theme cookie server-side
against `^[a-z]{1,10}(-[a-z]{1,10}){0,5}$` — lowercase letters and hyphens
only, no digits, segments of at most ten characters. Sheets are emitted as
`sv-<world>`, and a name that fails the pattern is rejected with exit code 2
rather than producing a file that installs and can never be selected.

**Values are validated, not trusted.** The sheet is built by string
interpolation, so `emitExtJsCss` requires hex colors, kebab-case token names, a
selectable theme name, and scale values free of `;`, `{`, `}` or comment
delimiters — and throws otherwise, the same way it already refuses to emit a
sheet with a missing token. A world theme is untrusted data here exactly as it
is in `src/lib/vernacular` and `src/lib/theme`, and the output lands in an
admin UI where injected CSS could overlay a confirmation dialog.

To do the same in-process:

```js
import { extJsInputsFromWorldTheme, emitExtJsCss } from '@svnbjrn/design/extjs';
import base from '@svnbjrn/design/tokens/dark.tokens.json' with { type: 'json' };

/** @returns {{ok: true, value: string} | {ok: false, error: string}} */
export const sheetForWorld = (worldThemePackage) => {
  const inputs = extJsInputsFromWorldTheme(worldThemePackage, base);
  if (!inputs.ok) return inputs; // errors are values, as everywhere else
  return { ok: true, value: emitExtJsCss(inputs.value) };
};
```

## Deliberate divergences from the web components

The QSS adapter documents its own; these are the ExtJS ones.

- **Pixels, not rem.** ExtJS measures widget geometry in JavaScript. A rem
  value would tie every metric to the host page's root font size.
- **Crisp's base sizing is left alone.** Family, color, radius and chrome
  change; density does not. ExtJS's layout code is calibrated to crisp's
  pixel metrics, and moving the base size shifts everything downstream of it.
  Font-size tokens are applied selectively (tooltips, headers).
- **Focus rings are `box-shadow`, never a border swap.** The web components
  and the QSS sheet grow a 2px border and shed a pixel of padding to
  compensate; here that would relayout every sibling.
- **`background-image: none` throughout.** Crisp paints gradients on buttons,
  headers and tab bars that would otherwise sit on top of our flat surfaces.
- **Invalid fields get a border, not crisp's squiggle.** The red underline is a
  background image, and clearing gradients clears it too; the error color moves
  to the border and the message text instead.
- **Interaction states are inlined hex, not `color-mix()`.** Same oklab math
  as `prepare.mjs` (`HOVER_MIX` 15%, `PRESSED_MIX` 25%), so the values match
  the Qt sheet byte for byte and the CSS stays readable by anything that
  parses it back.
- **Icon sprites are inverted on dark themes.** Crisp ships raster icons that
  are dark on transparent; `--sv-icon-filter` inverts them, the same trade the
  official Proxmox dark theme makes. It is imperfect on colored icons.
  Font-glyph icons (FontAwesome) are colored instead, never filtered.
- **Charts get eight `--pwt-*` variables.** RRD charts and gauges are drawn on
  canvas by JavaScript that reads `--pwt-panel-background`, `--pwt-text-color`,
  `--pwt-gauge-default`, `--pwt-gauge-back`, `--pwt-gauge-warn`,
  `--pwt-gauge-crit`, `--pwt-chart-primary` and `--pwt-chart-grid-stroke` with
  `getPropertyValue`. CSS cannot reach them any other way, so these are plain
  `var()` chains — never `color-mix()`, which the canvas side cannot parse.

## Verifying a change

`scripts/extjs-preview.html` renders the styled widgets against ExtJS from a
CDN; open it directly in a browser and switch its `<link>` between the dark and
light sheets. It lives under `scripts/` so it stays out of the published
package. It is a development aid, not a regression test — the real target is a
node.

On a throwaway VE or PBS instance, walk: login window, navigation tree,
resource grid (row striping, hover, selection, column headers), a summary
panel with gauges and RRD charts (the `--pwt-*` acid test — if these stay
light, a variable is missing), the task log viewer (monospace), a context
menu, a tooltip, and one form dialog. Repeat with the light sheet and one
generated world theme.

## Not covered

Svelte components, the React bridge, Vermis and Carter (their identity lives in
per-component markup and SVG assets, not just tokens), vernacular catalogs, the
ExtJS modern toolkit, and Proxmox Datacenter Manager. The `--sv-syn-*` syntax
tokens are emitted for completeness but nothing in ExtJS consumes them.
